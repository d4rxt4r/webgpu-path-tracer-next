# Приёмка этапа 10

Все показатели относятся к локальной Windows-машине с WebGPU-адаптером `intel gen-12lp`. Исходные настройки, линейные изображения и результаты скриптов хранятся в `docs/validation/`. Воспроизводимость означает фиксированные сцены, seed и параметры; время зависит от оборудования, браузера и текущей нагрузки.

## Численная проверка конечной Suzanne

[Результаты](validation/stage10-quality.json) получены при 32×24 пикселях, 2048 спектральных SPPM-итерациях, 8192 испущенных путях на итерацию и пакетах по 4096. Seed — 17, базовая глубина — 32, радиус — 0.03 м. Каждый вариант использует 16 777 216 фотонных путей. Raw-данные не фильтруются и не ограничиваются диапазоном отображения.

Эталон — PBRT v4 commit `b4ce9687e6c695f5582997c61b0c66cf064bdb4a`, CPU volpath depth64, 32768 spp, независимые seed17 и seed29. Экспорт сохраняет те же мировые треугольники, нормали, камеру, спектры отражения, эмиссии, Sellmeier и поглощение. [Сжатая сцена](validation/stage10-suzanne.pbrt.gz) и SHA-256 исходного текста позволяют проверить входные данные. Film использует CIE1931 sensor, linear sRGB, согласованный масштаб и отключённый white balance.

| Область | Расхождение двух PBRT seed | Ошибка средней Y SPPM относительно среднего PBRT |
|---|---:|---:|
| Пол под Suzanne | 0.62% | 2.63% |
| Центральная часть комнаты | 0.16% | 1.71% |
| Область стеклянного объекта | 0.12% | 2.52% |

Линейный luminance RMSE всего кадра — 0.01297. Критерий контрольной области пола: разброс эталонов ≤2%, ошибка SPPM ≤5%; он выполнен. Два seed показывают эмпирическую устойчивость, но не задают доверительный интервал для каждой точки изображения. Область пола включает каустическое и обычное освещение, отдельное разложение каустического вклада не выполнялось.

Глубина 64 вместо 32 оставляет среднюю Y пола неизменной в этом запуске; изменение средней комнаты — 0.0045%, luminance RMSE между глубинами — 0.0000861. Начальный радиус 0.06 вместо 0.03 м меняет среднюю Y пола на 0.73%; ошибка относительно PBRT — 1.91%, luminance RMSE — 0.00991. Больший радиус уменьшает шум и увеличивает пространственное сглаживание; эти два измерения не доказывают монотонную сходимость по любому радиусу.

## Изображение и фильтр

[Raw PNG](validation/stage10-final-raw.png), [фильтрованный PNG](validation/stage10-final-filtered.png), [линейный PFM](validation/stage10-final.pfm) и [параметры/сходимость](validation/stage10-final.json) сохраняются отдельным скриптом. PNG использует экспозицию 0, Reinhard и sRGB; PFM сохраняет исходные линейные компоненты, включая отрицательные. Финальный меш не упрощается.

Фильтр — реальный GPU à-trous с тремя проходами, strength2 и отключённым сглаживанием первых стеклянных поверхностей. Разница фильтрованного кадра с raw измеряет изменение отображения, а не ошибку относительно ground truth. Браузерная проверка подтверждает неизменность raw-накопления и стеклянных пикселей. Raw-кадр используется для проверки читаемого объёма, отражений стен и источника, преломлённого фона и светового рисунка на полу. Пространственный фильтр не является доказательством физической корректности.

Финальный кадр — 256×192, 2048 итераций, 33 554 432 испущенных пути, seed17, depth32, radius0.03. Все пиксели имеют полное число samples, ошибок GPU нет. Средняя Y области пола на 128/256/512/1024/2048 итерациях: 0.263204 / 0.263883 / 0.264131 / 0.263873 / 0.263465. Изменение 1024→2048 — около 0.15%; это сходимость одной последовательности, а не независимый доверительный интервал. Средняя Y всего raw — 0.239202, после фильтра — 0.238151 (−0.44%). Luminance RMSE изменения отображения — 0.145685, включая яркие границы источника. Raw сохраняет видимый Monte Carlo шум.

## BVH и перекрытие стенами

Выбор изображения, нормалей, глубины и BVH находится в начале боковой панели настроек. BVH-визуализация показывает число посещённых узлов на видимом участке луча до первой поверхности. Это тепловая карта обхода, а не геометрические линии всех bounding boxes.

Полный поиск ближайшего попадания может посещать скрытые ветви до обнаружения стены; прежняя тепловая карта показывала силуэт головы даже при правильном ближайшем попадании в стену. Диагностический проход теперь ограничивается расстоянием до первой поверхности.

[Численная проверка](validation/stage10-occlusion.json) сравнивает GPU с CPU brute force для 294 лучей реальной Suzanne: спереди, сзади, слева, справа, сверху и снизу. На пяти закрытых сторонах первая поверхность — стена коробки. Спереди центральный луч попадает в Suzanne через открытый проём. Сохранены и визуально просмотрены [front](validation/stage10-bvh-front.png), [back](validation/stage10-bvh-back.png), [left](validation/stage10-bvh-left.png), [right](validation/stage10-bvh-right.png), [top](validation/stage10-bvh-top.png) и [bottom](validation/stage10-bvh-bottom.png). Ошибок пересечений нет.

## Браузер, память и жизненный цикл

[Отчёт runtime](validation/stage10-runtime.json) содержит точные версии браузеров, настройки, память, порции GPU и время завершения. Chrome и Edge проверяются на production-сборке, обслуживаемой локальным статическим HTTPS-сервером. Временный self-signed сертификат используется только на loopback; автоматизация пропускает проверку доверия сертификату. Публикация на внешнем хостинге не выполнялась.

Firefox проверяется отдельным браузером Playwright. Наличие `navigator.gpu` само по себе не означает поддержку: требуется доступный адаптер. Если адаптер недоступен, приложение показывает понятную ошибку. Safari на Windows недоступен; совместимость с ним не заявляется.

Браузерные тесты проверяют фактическое уничтожение GPUDevice и восстановление нового устройства из CPU-сцены с сохранением режима и паузы, работу без timestamp-query/shader-f16/subgroups, стандартные device limits, DPR3 с ограничением backing resolution, повторные смены PT/SPPM и сцен без роста постоянных ресурсов, visibilitychange и ручную паузу. Изменение `document.hidden` в тесте проверяет обработчик приложения; поведение ОС при сворачивании окна отдельно не измерялось. Device.destroy воспроизводит реальное освобождение устройства; принудительный сбой драйвера не выполнялся.

## Профилирование интегратора

Отдельный замер без конкурирующих GPU-задач использует Suzanne и production-планировщик. Preview накапливает 16 spp, Reference — 4 spp, Quality — 4 полные итерации. Время включает initialization, очередь и планирование; это короткий запуск, не устойчивый FPS benchmark.

| Профиль | Внутренний размер | Постоянная память | GPU-порция median / p95 / max, мс | Полное время, с |
|---|---|---:|---:|---:|
| Preview | 160×120 | 12.31 MiB | 7.41 / 10.88 / 11.27 | 0.358 |
| Reference | 640×480 | 32.08 MiB | 4.52 / 8.19 / 11.27 | 4.306 |
| Quality | 640×480 | 67.46 MiB | 0.13 / 0.26 / 45.29 | 25.082 |

Timestamp-query охватывает команды интегратора, исключая отдельный display/denoise submission. Время завершения включает очередь/readback и отображение завершённого кадра; median/p95/max для Quality — 3.9 / 8.2 / 48 мс. `nextPhase` в списке порций — состояние после выполненной порции, не её классификация.

По результатам калибровки PT использует 48×48, SPPM camera/gather — 64×64 вместо 128×128. Накопление неподвижной камеры больше не ждёт отдельного RAF для каждого тайла: таймер запускает следующую порцию после завершения предыдущей. Preview остаётся привязан к RAF. Число задач в работе не увеличивается. Длинные порции до 45 мс сохраняются: цель 4–8 мс не является достигнутым верхним пределом для всех работ. Радиус, глубина и размер фотонного пакета доступны для дальнейшего выбора компромисса качества и задержки.

## Воспроизведение

```powershell
npm ci
npm test
npm run build
npm run test:browser
npm run validate:quality -- --pbrt C:/path/to/pbrt.exe
npm run capture:final
npm run capture:bvh
npm run validate:runtime -- --openssl C:/path/to/openssl.exe
```

Для Firefox: `npx playwright install firefox`. Chrome и Edge должны быть установлены. PBRT требуется указанного commit; OpenSSL создаёт временный сертификат локальной HTTPS-проверки. Скрипты владеют своими серверами и браузерами и завершают их после работы. Производительность измеряется отдельно, без параллельного GPU-рендеринга. Numerical SPPM runner работает без RAF и использует до 32 queued submissions; это инструмент численной проверки, а не интерактивный планировщик приложения с одной порцией в работе.

Итоговые проверки: 28 CPU-тестов, 31 браузерный тест и production build прошли. Базовый путь остаётся без аппаратного ray tracing и обязательных optional features. Конечная глубина, текущий радиус SPPM и Monte Carlo шум ограничивают точность. 4K, мобильные устройства, вложенные среды, rough glass и универсальный импорт остаются за рамками первой версии.
